# MC68882 FPU — Phased Scope Plan

## Status: Phase 0 and Phase 1 complete. Phase 2 (CIR bus-cycle timing) is next.

## Origin

This project is a companion to a separate, sibling project — a
cycle-accurate MC68030 CPU implementation (`MH030`, local path
`/Users/malcolm/MH030`) — but is deliberately its OWN repository, not a
subdirectory of that one. User request that established this repo
(verbatim, 2026-09-15): *"ok, in the docs section you will fins the
68881/2 user manual. Lets build a 68882 in verilog. It should be a
companion to the 68030 .. ie separate - but able to use together or with
someone else's 68030 simulation. The top leve should be pin compatible
with the original chip. Timings should be, as per the 68030 simulation,
extremely accuarate. Note that you dont have to run the 68882 from the
cpu clock, it could be its own clock .. so we need to create anew 4x
clock signal for the 68882. Please scope this out in phases"* — followed
by an explicit decision to make this a separate repo rather than a
subdirectory, since that's the more honest expression of "separate but
able to work together" than sharing a repo with the 68030 project would
be.

Source: `docs/MC68881_MC68882_Floating-Point_Coprocessor_Users_Manual_1ed_1987.pdf`
(396 pages, scanned/OCR'd) — copied from the MH030 project's own `docs/`.

## Hard requirements (from the user's own words)

1. **Standalone/companion, not tightly coupled** — usable with the
   MH030 project's own 68030, or with a third party's independent 68030
   implementation. No dependency on any other project's internal RTL,
   only on the documented CIR bus protocol (a plain bus-slave contract).
2. **Pin-compatible top level** — the real physical MC68882 signal list,
   not an abstracted interface.
3. **Cycle-accurate timing**, to the same standard already established
   for the MH030 project's own 68030 (pin-level S-state accuracy,
   confirmed against the manual, not assumed).
4. **Independent clock domain** — does not need to share a host CPU's
   clock; needs its own new 4×-multiplied internal clock derived from
   the FPU's own `CLK` pin (mirroring, but NOT reusing or depending on,
   MH030's existing "run RTL at 4× the external bus frequency"
   convention).

## Facts confirmed against the manual so far (grounding for the phases below)

**Pins** (68-pin PGA; logically what matters): `A0-A4` (5-bit CIR select,
input, no on-chip FC/CPU-space decode), `D0-D31` (bidirectional,
3-state), `SIZE` (input, active-low, port-width strap), `AS` (input,
active-low), `CS` (input, active-low — generated by EXTERNAL glue logic;
no dedicated CS-generation logic exists inside the FPCP), `R/W` (input),
`DS` (input, active-low), `DSACK0/DSACK1` (output, active-low,
3-state), `RESET` (input, active-low), `CLK` (input, plain TTL square
wave, no gating/stretching), `SENSE` (optional input/output). No
BERR/interrupt/FC/RMC/ECS/OCS/DBEN/HALT/BR/BG/BGACK/IPL pins — a
register-mapped bus slave from the main CPU's perspective, far simpler
than a 68030's own pin interface.

**CIR map** (A4-A0 offsets): Response $00 (16-bit,R), Control $02
(16-bit,W), Save $04 (16-bit,R), Restore $06 (16-bit,R/W), Operation
Word $08 (16-bit,W, unused/dead for this FPU), Command $0A (16-bit,W),
(reserved) $0C, Condition $0E (16-bit,W), Operand $10 (32-bit,R/W),
Register Select $14 (16-bit,R), (reserved) $16, Instruction Address $18
(32-bit,W), Operand Address $1C (32-bit,R/W, unimplemented/dead).

**Host-side CPU-space coprocessor decode** (for reference — this is the
HOST's job, not this chip's; confirmed to match the MH030 project's own
already-documented understanding): FC=111 (CPU Space), A[19:16]=0010
(Coprocessor Communications), A[15:13]=Cp-ID (matches the F-line op
word's own bits[11:9]; Motorola default Cp-ID=001 for FPU). This FPCP
itself has no FC pins and does no CPU-space decode at all — it only ever
sees `A0-A4` (the CIR select) plus `CS`, which some external glue must
already have decided to assert.

**Three bus cycle types** (Section 10.4 — the core cycle-accuracy
foundation):
1. **Synchronous Read** (Response $00 and Save $04 ONLY) — gated by the
   FPCP's OWN internal `CLK` sampling `AS`+`DS`+`CS`; DSACK asserts 1½
   clocks after all three sampled asserted; 5-clock baseline (2 wait
   states beyond minimum per Figure 10-6), can extend to 6-7 clocks
   depending on clock-edge relationship — documented normal variability.
   This is the cycle type that most directly requires this chip's own
   half-clock-tick-resolution internal 4× clock.
2. **Asynchronous Read** (all other CIR reads) — dual-ported internally,
   DSACK timing independent of FPCP clock frequency; 3-clock/no-wait-
   state baseline (Figure 10-7).
3. **Asynchronous Write** (any write) — same dual-ported/clock-
   independent model; 3-clock/no-wait-state baseline (Figure 10-8),
   DS-pulse-triggered.

**Chip-Select timing** (Section 10.3): early CS (preferred) vs. late CS
(adds wait states); CS must be stable during AS/DS transitions; cycle
start = AS+CS+(DS-or-R/W) all asserted; cycle end = first of AS/DS
negates.

**Inter-cycle timing restrictions** (Section 10.5): 4 bus-cycle types
trigger internal processing on DS's negated edge, completing within 4
clocks (write to Control CIR LSB; write to Restore CIR LSB; last Operand
CIR write during a busy-frame restore; first Operand CIR read during an
idle/busy-frame save) — a subsequent async access issued before that
completes gets its own DSACK delayed. Plus 2 general "main-processor-
overrun" delay cases with no fixed clock bound.

**Response Primitive protocol** (Section 7.4.2): 16-bit word from
Response CIR; bit[15]=CA (come-again), bit[14]=PC (pass-PC-now),
bit[13]=DR (direction), bits[12:0]=primitive-specific. This FPU uses 6 of
the 18 general M68000-coprocessor primitives: Null, Evaluate-EA-and-
Transfer-Data, Transfer-Single-Main-Processor-Register, Transfer-
Multiple-Coprocessor-Registers, Take-Pre-Instruction-Exception,
Take-Mid-Instruction-Exception.

**State Frames** (Section 6.4.2, FSAVE/FRESTORE): Null (4 bytes),
Idle (68881: 24B; 68882: 56B = 24+32B extra CU-state, inserted right
after the format word), Busy (68881: 180B; 68882: 212B = 180+32B extra
CU-state). All 3 share the same first-longword shape: reserved word +
format word (version byte + state-size byte).

**Programming model**: FP0-FP7 (80-bit extended), FPCR (exception-enable
byte + mode-control byte), FPSR (condition-code byte + quotient byte +
exception-status byte + accrued-exception byte), FPIAR. Exception
status/enable byte bits[15:8] = BSUN,SNAN,OPERR,OVFL,UNFL,DZ,INEX2,INEX1.
Mode control byte: bits[7:6]=Rounding Precision, bits[5:4]=Rounding Mode.

**68881 vs 68882 architectural differences** (directly load-bearing
since this project targets the 68882 specifically):
1. 68882 has a genuine 3-stage internal pipeline — **BIU** → **CU**
   (conversion unit, format conversions to/from internal extended
   precision) → **APU** (arithmetic processing unit). 68881 has only
   BIU+APU. Confirmed directly (Section 1.2/1.2.1 block-diagram text):
   "the MC68882 has a conversion unit (CU) that performs data format
   conversions to the internal extended format. The CU relieves the APU
   of a significant work load and allows the MC68882 to execute FMOVE
   instructions concurrently with arithmetic or transcendental
   operations."
2. **Concurrency model** (Section 5.1.1, confirmed directly): both chips
   let the main processor proceed past a floating-point instruction once
   its transfer phase completes (response CA=0). The 68881 can only ever
   have ONE instruction in flight (in the APU) — if the main processor
   issues a second FP instruction while the first is still executing,
   the 68881 stalls it with a null (CA=1,IA=1) response until the APU
   frees. The **68882 additionally lets the BIU hand a second
   instruction to the CU** while the first is still executing in the
   APU — the CU stages/converts operands (for B/W/L/P operand formats,
   see Table 5-1's "Minimum-Concurrency Instructions": FMOVE, FMOVECR,
   FMOVEM, FTST forms) and waits for the APU to free before handing off
   — genuine 2-deep pipelining, not just faster single-instruction
   dispatch.
3. **Control CIR AB/XA semantics differ**: 68881 = any write is an
   unconditional total abort (undefined destination register, clears
   exceptions, resets BIU to idle). 68882 = separate AB (abort, only
   meaningful within a defined "abort window," terminates ONLY the
   instruction the window applies to, letting any OTHER concurrently
   in-flight pipeline-stage instruction complete) vs. XA (exception-
   acknowledge; the handler must ALSO independently clear the underlying
   condition or the FPCP re-reports it).
4. **Instruction Address CIR / PC transfer**: optional for 68881;
   MANDATORY for 68882 (protocol violation if omitted) — because the
   68882 has 3 SEPARATE per-pipeline-stage instruction-address
   registers, with FPIAR being specifically the APU-stage one (only APU
   reports exceptions).
5. **CA-bit flexibility**: 68881 always uses CA=1 for every non-null
   primitive; 68882 may issue Evaluate-EA-and-Transfer-Data with CA=0
   where skipping the automatic Response-CIR recheck is still correct
   (a pipelining optimization).
6. **State frame sizes**: 68882's Idle/Busy frames are each 32 bytes
   larger than 68881's, to hold CU-internal state.

**APU/CU concurrent-exception attribution** (Section 7.5.4.2, now read in
full): when an instruction executing in the APU concurrently with
another instruction in the CU causes an exception, the CU-held
instruction reports it as a **mid-instruction exception when the CU
instruction itself later completes** — not immediately when the APU's
own exception actually occurs. The main processor's next Response CIR
read (for what it thinks is the CURRENT, CU-held instruction) returns a
take-mid-instruction-exception primitive instead. Critically: **the
write-exception-acknowledge operation does NOT itself cause a null
primitive** — only the exception handler's own **FSAVE** instruction
changes the primitive back to null. If the handler omits FSAVE, the
take-mid-instruction-exception primitive persists and the NEXT
floating-point instruction re-takes the same exception again (Figure
7-34's own "incomplete handler" case) — a real, easy-to-get-wrong
protocol trap this RTL must model faithfully (Phase 6), not simplify
away. Related: a mid-instruction INTERRUPT (Section 7.5.4.3, not just
exception) can also land during an `FMOVE FPm,<ea>` calculation phase —
the dialog resumes correctly across it, but the manual explicitly warns
that **casually reading the Response CIR to poll status mid-dialog is
invalid** (it would discard the pending primitive and corrupt the
suspended protocol); the only valid status check is FSAVE (examine the
frame) then FRESTORE (reinstate). This "FSAVE/FRESTORE are the only safe
way to peek at FPCP state mid-dialog" rule is a real constraint on how
Phase 6/7's own verification harness may probe internal state without
disturbing it.

## Companion-project integration context (informational — not part of
this project's own required scope; see Phase 8)

The sibling MH030 project's RTL already implements the CIR access bus
protocol and cpSAVE/cpRESTORE's full state-transfer handshake on the
68030 side, but has no dedicated CS-equivalent output pin of its own —
any real attachment of this FPU needs a small external glue/decode
module (`FC=111 && A[19:16]=$2 && A[15:13]=CpID → CS_n`) that exists in
neither project today. MH030's own `CLAUDE.md` documents, as a standing
deliberate scope boundary, that the 68030-side coprocessor-conditional
instructions (cpBcc/cpDBcc/cpScc/cpTRAPcc) and Coprocessor Protocol
Violation (vector 13) are unimplemented/untested specifically because
testing them needs a real attached coprocessor model, which that project
never built. This repo is the missing piece to eventually close that gap
on the MH030 side — a later, optional integration opportunity for
WHOEVER pairs the two, not a requirement for this project's own phases
to be considered complete on its own terms.

## Phases

### Phase 0 — Spec foundation (research complete, writing CLAUDE.md next)
Freeze the facts above into `CLAUDE.md` at this repo's root, written the
same reference-doc style the MH030 project uses for its own 68030 (pin
list, CIR map, S-state timing tables, inter-cycle restrictions, primitive
protocol, state frame formats, 68881-vs-68882 differences, including the
APU/CU concurrent-exception attribution rule above). This is what makes
this repo genuinely standalone-readable on its own, with no dependency
on MH030's own docs to understand it.

### Phase 1 — Clock domain and pin-level BIU skeleton (COMPLETE)
`rtl/m68882_top.sv` with the real pin list, `rtl/m68882_sync.sv` (generic
2-stage synchronizer, one instance per host-driven input: `AS`, `DS`,
`CS`, `R/W`, `SIZE`, `A0-4`), and `rtl/m68882_biu.sv` (recognizes a
`CS`+`AS`+`DS` cycle boundary and sources `DSACK0/1`, asynchronous-cycle
model only — no CIR content yet, Phase 2).

**Finding**: no separate clock-multiplier module was built or needed.
`clk_4x` is simply a plain top-level input port, supplied already-
multiplied by the testbench/environment — exactly mirroring MH030's own
`m68030_top.sv` convention (its own port is literally named `clk_4x`
too). A literal on-chip PLL that multiplies a slower `CLK` pin up to 4x
is out of scope for a cycle-accurate RTL *simulation* model on either
project — MH030 never built one either, and there was no reason for this
project to be the first. This chip's `clk_4x` is a wholly separate port
from MH030's own, with no fixed relationship enforced between them —
satisfying the "own clock" requirement without needing new clock-
generation RTL.

**Verified**: `tb/m68882_biu_smoke_tb.sv` (raw pin-level drive, no host
CPU — mirrors MH030's own `tb/biu_tb.sv` convention for a first-cut BIU
test) — 8/8 checks pass via `make test` (Icarus Verilog): read and write
cycle recognition, `DSACK0/1` polarity (a fixed 16-bit-port placeholder,
to be replaced with real per-CIR width in Phase 2), bounded assert
latency (2-stage synchronizer + 1 detect register, confirmed within a
2-6 tick window), and correct negation once the host releases `AS`/`DS`/
`CS`.

### Phase 2 — CIR bus-cycle timing (the accuracy-critical phase)
Implement the CIR register file and get all three bus-cycle types
S-state-exact against Figures 10-6/10-7/10-8: synchronous read
(Response/Save, 1½-clock-after-sample DSACK delay, 5-clock baseline with
real wait-state variability), asynchronous read (3-clock baseline,
clock-frequency-independent), asynchronous write (3-clock baseline,
DS-pulse-triggered). Implement the Section 10.5 inter-cycle restrictions
(Control/Restore LSB writes, Operand CIR sequencing under busy-frame
save/restore). Budget a `timing_diagrams/` pass here, same methodology
MH030 uses for its own — that process has repeatedly caught real S-state
bugs there and should be expected to do the same here.

### Phase 3 — Programming model and primitive protocol (no real math yet)
FP0-FP7 (80-bit), FPCR/FPSR/FPIAR, Command CIR op-word decode, Response
Primitive generation for all 6 primitives this FPU uses, Condition CIR
evaluation. Arithmetic results can be stubbed/pass-through — this phase
is entirely about the CIR handshake protocol (CA/PC/DR bits, primitive
sequencing) independent of computed-value correctness. This is also the
phase that later enables real testing of MH030's own cpBcc/cpDBcc/cpScc/
cpTRAPcc gap (see integration note above) — not itself required here.

### Phase 4 — Real arithmetic core (APU)
Extended-precision datapath: format conversion, add/sub/mul/div/sqrt,
the full transcendental set, rounding modes, all 8 exception flags. The
largest phase; needs its own sub-phasing (basic arithmetic first,
transcendentals second). **Open scoping question, to resolve before
starting this phase**: real 68881/68882 silicon's transcendental results
follow Motorola's own specific approximation algorithms, which can
diverge from a generic IEEE-correct softfloat implementation in the last
bit or two — decide up front whether the target is "matches real chip
output bit-for-bit" or "IEEE-correct," since it changes both the
implementation effort and the Phase 7 reference-model choice.

### Phase 5 — State frame save/restore
FSAVE/FRESTORE Null/Idle/Busy frame generation and parsing, both
chip-variant sizes (68882's extra 32-byte CU-state block after the
format word). Needed for any context-switch testing against a host CPU
later.

### Phase 6 — 68882-specific pipelining (BIU → CU → APU overlap)
The genuine 68882 differentiator (Section 5.1.1, confirmed above): the
CU accepts and stages a second arithmetic instruction (converting B/W/L/P
operands, prefetching via the BIU) while the APU is still busy with the
first, then hands off once the APU frees. Also: per-pipeline-stage
Instruction Address tracking (mandatory PC transfer), AB abort-window
semantics vs. XA exception-ack, CA=0 optimization opportunities, and the
still-unread APU/CU-concurrent-exception-attribution nuance flagged
above. Deliberately sequenced last — a concurrency/overlap layer on top
of a protocol and arithmetic core that must be correct and functionally
complete first; Phases 1-5 alone already give a fully correct, just less
concurrent, 68882.

### Phase 7 — Verification harness
Mirror MH030's own trace-driven co-simulation methodology. MH030's own
`tools/musashi/` already includes 68881/2 FPU emulation (softfloat-
based) — the natural golden reference, reusable without building a
second one (this repo would need its own copy/build of Musashi, or a
documented path to MH030's). Bus-cycle-log diffing the same way MH030's
`run_harte.py`/`cosim_grp` already work, plus a dedicated arithmetic-
result comparison pass MH030 never needed (its own harness only ever
checked integer/bus correctness).

### Phase 8 — Companion integration example (optional, last)
A small external glue module (`FC=111 && A[19:16]=$2 && A[15:13]=CpID →
CS_n`) and example top-level wiring attaching this chip to the MH030
project's own 68030 (as a sibling checkout or git submodule, never a
code dependency) — demonstrating the "separate but able to work
together" requirement concretely. Also the natural point to circle back
and close MH030's own long-documented coprocessor-conditional-
instruction gap, now that a real coprocessor exists to test against —
flagged as a follow-on opportunity for that project, not required for
this one to be complete.
