# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

This is a cycle-accurate Motorola MC68882 floating-point coprocessor
(FPCP) implementation in SystemVerilog/Verilog. It is a **standalone
companion project** to a separate sibling repository, `MH030` (a
cycle-accurate MC68030 CPU, local path `/Users/malcolm/MH030`) — but is
deliberately independent: this repo has no code dependency on MH030's
RTL, only a shared understanding of the M68000 Family coprocessor bus
protocol (a plain, documented bus-slave contract). It must work either
paired with MH030's own 68030, or with any third party's independent
68030/68020 implementation.

Source manual: `docs/MC68881_MC68882_Floating-Point_Coprocessor_Users_Manual_1ed_1987.pdf`
(396 pages, scanned/OCR'd). See `plan.md` for the phased build-out plan
and its own research provenance.

## Design Constraints

**Pin compatibility**: the top-level module must expose the real
physical MC68882 signal list (below), not an abstracted interface — this
chip must be a drop-in bus slave from any host's perspective.

**Independent clock domain**: this chip's own `CLK` pin has NO fixed
relationship to any host CPU's own bus clock — real systems may tie them
to the same oscillator, but architecturally they are independent inputs.
Internally, run this RTL at **4× the external `CLK` frequency**
(mirroring MH030's own "4× the external bus frequency" convention, but
as a wholly separate, second clock-multiplier instance — never derived
from or synchronized to a host CPU's own internal clock).

**Every bus input must be synchronized**: because a host may run a
genuinely unrelated clock, `AS`, `DS`, `CS`, `R/W`, and `SIZE` all need
2-stage synchronizer flip-flops before any logic uses them — broader
than MH030's own convention (which only synchronizes error/arbitration
lines), since here there is no shared-clock guarantee at all. All logic
synchronous, no latches, no asynchronous resets (same baseline rule
MH030 uses).

**No cheating cycles**: if a cycle takes N clocks on real silicon per the
manual's own S-state tables (below), the FSM must take exactly N clocks.

perspective — it never masters the bus, never signals its own errors
directly to a bus, and has no interrupt input of its own.

## Bus Cycle Timing — the cycle-accuracy foundation (Section 10.4)

There are exactly **three** bus cycle types, and which one applies
depends on WHICH CIR is being accessed, not on any external signal:

**1. Synchronous Read** — Response ($00) and Save ($04) ONLY. Genuinely
gated by this chip's OWN internal `CLK` — it samples `AS`+`DS`+`CS` on
its own clock edge, and `DSACKx` asserts **1½ clocks after all three are
sampled asserted**. Baseline is **5 clocks** (2 wait states beyond the
theoretical minimum, per Figure 10-6's own S0-S5 sequence with Sw states
inserted), and can extend to 6-7 clocks depending on the phase
relationship between the host's own AS/DS edges and this chip's internal
clock edge — this is documented, expected variability, not a bug to
"fix away." This is the cycle type that most directly justifies this
chip's own multiplied internal clock: half-clock-tick timing resolution
is needed to model the 1½-clock DSACK delay accurately.

**2. Asynchronous Read** — every other CIR read (Restore, Command is
write-only so N/A, Condition is write-only so N/A, Operand, Register
Select, Instruction Address is write-only so N/A). Dual-ported
internally — DSACK timing is fully independent of this chip's own clock
frequency. Baseline **3 clocks, 0 wait states** (Figure 10-7's own S0-S5).

**3. Asynchronous Write** — any write to any CIR. Same dual-ported,
clock-independent model. Baseline **3 clocks, 0 wait states** (Figure
10-8's own S0-S5), DS-pulse-triggered (the write completes on DS's own
assert/negate pulse, not a clock-relative sample).

**Chip-Select timing** (Section 10.3): "early CS" (CS asserts before AS
— preferred, minimizes latency) vs. "late CS" (CS follows AS — adds wait
states, allows simpler/cheaper external decode logic). CS must remain
stable across the AS/DS transition. A bus cycle starts when
`AS`+`CS`+(`DS`-or-`R/W`) are all asserted; it ends at the first of
`AS`/`DS` negating.

**Inter-cycle timing restrictions** (Section 10.5) — 4 specific bus-cycle
types trigger internal processing on the NEGATED edge of `DS`, completing
within 4 clocks; a subsequent asynchronous access issued before that
internal processing finishes gets its own DSACK delayed until it does:
1. Write to the Control CIR's low byte (LSB).
2. Write to the Restore CIR's low byte (LSB).
3. The LAST Operand CIR write during a busy-frame restore.
4. The FIRST Operand CIR read during an idle/busy-frame save.

Two further, less bounded cases exist (no fixed clock count, just "this
chip doesn't respond until internally ready"): a main-processor
Operand/Register-Select CIR read issued before the chip is ready, or an
Operand CIR write issued before the previous write value has been
internally stored.

## Response Primitive Protocol (Section 7.4.2)

A 16-bit word read from the Response CIR. General format:
`bit[15]=CA` (come-again — see below), `bit[14]=PC` (pass-PC-now —
requests the host write the Instruction Address CIR), `bit[13]=DR`
(transfer direction), `bits[12:0]` = primitive-specific payload.

Of the 18 primitives the general M68000 coprocessor architecture defines,
this chip uses exactly 6: **Null**, **Evaluate-EA-and-Transfer-Data**,
**Transfer-Single-Main-Processor-Register**, **Transfer-Multiple-
Coprocessor-Registers**, **Take-Pre-Instruction-Exception**,
**Take-Mid-Instruction-Exception**.

**CA (come-again) semantics**: CA=1 means this chip cannot yet proceed
concurrently with main-processor instruction execution — the host must
perform the indicated service, then re-read the Response CIR. CA=0
releases the host to proceed to its own next instruction once it has
performed the indicated service (the arithmetic instructions release the
host once their transfer phase completes).

## Programming Model

- **FP0-FP7**: 80-bit extended precision, general-purpose.
- **FPCR** (32-bit): exception-enable byte + mode-control byte.
  - Mode control byte: `bits[7:6]` = Rounding Precision (00=Extended,
    01=Single, 10=Double, 11=reserved), `bits[5:4]` = Rounding Mode
    (00=Nearest, 01=Toward-Zero, 10=Toward-(-Inf), 11=Toward-(+Inf)).
- **FPSR** (32-bit): condition-code byte + quotient byte +
  exception-status byte + accrued-exception byte.
  - Exception status/enable byte `bits[15:8]` = BSUN, SNAN, OPERR, OVFL,
    UNFL, DZ, INEX2, INEX1 (8 flags, MSB to LSB in that order).
- **FPIAR** (32-bit): instruction-address register — specifically the
  **APU-stage** address register on this chip (see pipeline note below);
  only the APU reports exceptions, so this is the one host-visible
  address register even though 3 exist internally.

## State Frames (FSAVE / FRESTORE, Section 6.4.2)

Three frame types, all sharing an identical first-longword shape
(low word = reserved/alignment, high word = format word = version byte +
state-size byte):

| Frame | Size | Meaning |
|-------|------|---------|
| Null | 4 bytes | Version=0 wildcard — "programmer's model is empty." |
| Idle | **56 bytes** (68881: 24 bytes) | Programmer's model is populated but no instruction is executing. The extra 32 bytes vs. the 68881 hold CU-internal state, inserted immediately after the format word — every field after that point sits at a +$20 offset vs. the 68881's own layout. |
| Busy | **212 bytes** (68881: 180 bytes) | An instruction is mid-execution. Same +32-byte/+$20-offset insertion rule as Idle. |

## MC68882-Specific Architecture (why this chip, not a 68881, was asked for)

**Three-stage internal pipeline** (Section 1.2/1.2.1): **BIU** (bus
interface unit) → **CU** (conversion unit — converts operands to/from
the internal extended-precision format) → **APU** (arithmetic processing
unit — performs the actual computation). The 68881 has only BIU+APU; the
CU is what lets this chip execute `FMOVE` concurrently with an
in-progress arithmetic or transcendental operation.

**Concurrency model** (Section 5.1.1): a 68881 can have only ONE
instruction in flight — if the host issues a second FP instruction while
the APU is still busy with the first, the 68881 stalls it with a null
(CA=1,IA=1) response until the APU frees, and cannot even begin
prefetching the second instruction's own operands. **This chip
additionally lets the BIU hand a second instruction to the CU** while the
first is still executing in the APU. The CU stages/converts that second
instruction's operands (for `B`/`W`/`L`/`P` operand-format instructions —
see the manual's own Table 5-1, "Minimum-Concurrency Instructions":
`FMOVE`, `FMOVECR`, `FMOVEM`, `FTST` forms) and waits for the APU to
become idle before handing off — genuine 2-deep pipelining, not merely
faster single-instruction dispatch.

**Control CIR AB (Abort) vs. XA (eXception-Ack) semantics** (differs from
the 68881, which has only a single unconditional-abort write semantic):
- **AB** is only meaningful within a defined "abort window" — from the
  Command CIR write through the last CIR access required for that
  specific instruction. Outside that window, AB's effect is undefined.
  When valid, AB terminates ONLY the instruction the window applies to —
  any OTHER instruction concurrently in flight in a different pipeline
  stage is left to complete normally.
- **XA** clears a pending exception in this chip's own state — but the
  exception handler must ALSO independently clear the underlying
  condition that caused it, or this chip will simply re-report the same
  exception on the next relevant check.

**Instruction Address CIR / PC transfer is MANDATORY** (a protocol
violation if the host omits it) — unlike the 68881, where it's optional
and simply never causes a violation if skipped. This chip maintains 3
SEPARATE per-pipeline-stage instruction-address registers (BIU/CU/APU);
the PC value written to the Instruction Address CIR "rides along" with
its own instruction through each pipeline stage, and FPIAR (the
host-visible one) is specifically the APU-stage register.

**CA-bit flexibility**: the 68881 always sets CA=1 for every non-null
primitive. This chip may issue an Evaluate-EA-and-Transfer-Data primitive
with CA=0 in cases where skipping the automatic Response-CIR recheck
doesn't affect correctness — a pipelining optimization the 68881 never
has the internal structure to make.

**APU/CU concurrent-exception attribution** (Section 7.5.4.2 — a real
protocol trap this RTL must model faithfully, not simplify away): when an
instruction executing in the APU concurrently with another instruction
in the CU causes an exception, the CU-held instruction reports it as a
**mid-instruction exception when the CU instruction itself later
completes** — not immediately when the APU's own exception condition
actually occurs. The host's Response CIR read (intending to check on
what it thinks is the CU-held, currently-dispatched instruction) instead
returns a take-mid-instruction-exception primitive. The
write-exception-acknowledge operation (XA, above) does **NOT** by itself
cause this chip to return a null primitive — only the exception
handler's own **FSAVE** instruction does that. If the handler omits
FSAVE, the take-mid-instruction-exception primitive persists and the
NEXT floating-point instruction re-takes the same exception. Related
(Section 7.5.4.3): an interrupt landing mid-`FMOVE FPm,<ea>` calculation
resumes correctly across the interrupt handler, but **casually reading
the Response CIR to poll status mid-dialog is invalid** — it discards
the pending primitive and corrupts the suspended protocol. The only
valid way to inspect this chip's state mid-dialog is FSAVE (examine the
frame) then FRESTORE (reinstate) — a real constraint on how this
project's own future verification harness (Phase 7) may probe internal
state without disturbing it.

## Style Rules

Same conventions as MH030: SystemVerilog (`always_ff`, `always_comb`,
`typedef enum`, `struct`), `generate` loops for replicated structures
(FP0-FP7), no combining two pipeline stages in one `always` block.

## Verification Approach (planned, Phase 7)

Trace-driven co-simulation, mirroring MH030's own methodology: MH030's
`tools/musashi/` already includes 68881/2 FPU emulation (softfloat-
based) as a golden reference. Bus-cycle-log diffing plus a dedicated
arithmetic-result comparison pass (MH030's own harness never needed this,
since it only ever checked integer/bus correctness).

## Data Bus Lane Placement (Section 9.8 — easy to get wrong)

Every 16-bit CIR is hardwired onto **D16-D31**, always — never D0-D15,
regardless of the register's own odd/even address, and regardless of
port size ("to eliminate the need for on-chip multiplexors," per the
manual's own stated rationale). 32-bit CIRs (Operand/Instruction-Address/
Operand-Address) span the full D31-D0. A 16-bit-bus host system wires its
own data bus to whichever half its own board design chose (D16-D31 or
D0-D15) — that's a system-integration detail this chip's own behavior
doesn't need to (and can't) account for.

**Two real bugs found and fixed while building Phase 2** (both confirmed
directly against the manual, not assumed — matching this project's own
established rigor standard):
1. **Phase 1's own DSACK polarity placeholder was wrong.** It modeled an
   8-bit-port ack, not a 16-bit one — Table 9-3 shows DSACK1#=asserted/
   DSACK0#=negated for a 16-bit port, the OPPOSITE of what Phase 1
   shipped. Found while grounding Phase 2 in the real table; fixed via
   `m68882_cir_pkg.sv`'s own table-driven `dsack_encode()` function
   instead of a hand-picked constant.
2. **A genuine write-data corruption bug**, found via simulation, not
   inspection: `m68882_cir.sv`'s original write logic gated the register
   update on the LEVEL of `write_strobe` (`cyc_ack && cyc_write`), which
   stays asserted for a few extra `clk_4x` ticks after a real host
   releases the data bus — an unavoidable consequence of this chip's own
   synchronizers lagging the host's AS#/DS# negation by up to 2 ticks
   (Phase 1's own design). The level-sensitive write kept re-latching
   `d_in` on those extra ticks, overwriting the just-written value with
   X/Z once the host tri-stated the bus. Fixed by edge-detecting
   `write_strobe`'s own rising edge (`write_pulse`) so the register
   latches exactly once per cycle — also the more faithful reading of
   Section 10.4.3's own wording ("an asserted pulse occurs on DS, the
   FPCP responds by ... latching the value").

**Scope boundary carried into Phase 3+**: 8-bit-port operation (needing a
genuine multi-cycle byte-sequencing state machine) and a 16-bit port
accessing a 32-bit CIR are both explicitly NOT implemented — this
project's real use cases (MH030, or any reasonable third-party 68030/
68020 host) are 32-bit-bus systems. `dsack_encode()` returns a
protocol-correct code for the 8-bit case, but `m68882_cir.sv`'s own data
path doesn't implement the multi-cycle transfer that would actually be
needed to complete such a transfer.

(`m68882_apu_pkg::fp_mul`/`fp_div`): FMUL is a real 64x64->128-bit

bits, Verilog's own `/`/`%` used behaviorally, same house style as
`+`/`-`/`*` elsewhere in this file). Both renormalize into the same
64-bit window convention `fp_add_sub` established and round through the
identical `round_mantissa` task. FDIV also wires up FPSR's DZ bit (bit10
of the exception-status byte, the first exception-status bit this
project actually sets — OR'd in, not overwritten, a narrow first step
toward Phase 4d's own real accrued-exception-byte semantics). All 12 new
`tb/m68882_apu_tb.sv` checks (21/21 total) passed on the first run —
Phase 4a's own carry-out fix generalized cleanly to both, no repeat of
that bug.
